# Qwen3.5-0.8B "weight-space programming" fix as a Core AI mutable-weight adapter

All numbers below were measured on one Mac (macOS 27.0, Apple silicon GPU), unless marked
otherwise. Scripts, summaries and logs are in this directory. Large raw outputs (generation
JSONL, logits) and the exports are not committed (see `.gitignore`); every one of them is
regenerated by the scripts listed under Reproduce.
Labels: **[Core AI]** = run on the Core AI runtime; **[PyTorch]** = run in PyTorch.

## TL;DR

- **The fix runs on Core AI as an adapter that toggles without re-export.** The published
  edit is a rank-1 update on `layers.{15,19}.mlp.down_proj`. It is carried as four
  mutable-weight states (`l15_u, l15_c, l19_u, l19_c`) next to the model's own
  `keyCache / valueCache / convStates / recurrentStates`, in the stock macOS Qwen3.5 recipe
  (local wrapper; no public model file changed). The adapter is 18,432 bytes as dense fp16
  vectors (2,176 non-zero parameters). The `.aimodel` grows by 5.4 KB.
- **Parity [Core AI vs PyTorch].**
  - fp16 export: adapter on vs the *published edited checkpoint* gives max |Δlogit| 0.04 to
    0.18 and **100% top-1 agreement** over 117 teacher-forced positions on 6 prompts. Adapter
    off vs base gives 0.04 to 0.20 and 100%.
  - 4bit export: against the same 4-bit model in eager PyTorch, max |Δlogit| ≤ 0.22 and top-1
    agreement 98 to 100%. The adapter's effect correlates 0.9997 to 0.9999 with PyTorch's.
- **Cost [Core AI, 4bit].**
  - Toggling the adapter is a host-side fill of the four states: **0.022 ms**, with no
    re-export and no reload. The first decode step after a toggle costs the same as any other
    (3.99 vs 3.99 ms).
  - Decode throughput: 224.6 tok/s on, 226.4 off, 222.7 for the plain export. Prefill:
    3,441 / 3,412 / 3,302 tok/s.
  - A re-export takes 66 to 82 s, plus a first-load compile.
- **Generation [Core AI, 4bit, N=50 MATH-500, cap 8192].** The adapter cuts tail looping
  (loopstats tail repetition > 0.5) from **48/50 to 14/50** (paired exact McNemar
  p = 1.2e-10). The share that closes `</think>` rises from **1/50 to 21/50**
  (p = 1.9e-6). Accuracy is 1/50 vs 3/50 at this cap (p = 0.5, not significant). The 8192
  cap is far below what the edited model needs; the blog's edited model averages 21.7K
  tokens.
- **Not shown:** the blog's accuracy (7.9% → 48.1%). See the 32K run and caveats below.

## Setup

| item | value |
|---|---|
| base checkpoint | `Qwen/Qwen3.5-0.8B` (HF cache) |
| edited checkpoint | `RikiyaT/Qwen3.5-0.8B-weight-space-programming` |
| adapter | `rank1_edit.pt` → dense `u` (1024) and `c` (3584) per layer, `down_proj(h) + u·(cᵀh)`; scale s multiplies u; blog strength a = 6s |
| export | `coreai_export.py`: stock `coreai_models/models/macos/qwen3_5.py` loaded through the export pipeline, `down_proj` on layers 15 and 19 wrapped by `Rank1MutableAdapter[2D]` whose `u`, `c` are `MutableWeight`s read via `.read()`; `export_to_coreai(..., state_names=(l15_u, l15_c, l19_u, l19_c, keyCache, valueCache, convStates, recurrentStates))`, `main` + `prefill` entrypoints |
| presets | `none` (fp16) and `4bit` (coreai-opt INT4 per-block weights; adapter states stay fp16) |
| runtime | macOS 27.0 Core AI framework. Python `coreai.runtime` for parity; Swift driver `swiftgen/` (system CoreAI; GPU preferred + `expectFrequentReshapes`, same as the repo's Swift LLM runner) for parity, throughput and generation |
| generation | prompt via `prefill`, decode on `main` one token at a time; host sampling: presence_penalty 1.5 (vLLM convention: subtract from every token already generated), temperature 0.6, top_k 20, top_p 0.95; thinking on; stop on `<|im_end|>` / `<|endoftext|>` |

- Adapter export with the adapter off vs the plain export: **bit-identical** logits

Raw outputs: `results/gen_main.jsonl` (token ids, finish reason, timings) and
`results/gen_main.scored.jsonl` (decoded text, per-sample metrics). Decode ran at about
215 to 222 tok/s per sample.

What the texts show: base samples end in verbatim cycles (for example, the same sentence
repeated to the cap). Adapter samples more often finish the reasoning, close `</think>` and
write a boxed answer, but many then keep re-checking ("Final Answer: \boxed{4} … Wait.")
instead of emitting `<|im_end|>`. So "hit cap" barely moves at 8192.

**Cap 32768 run (blog setting): in progress** when this was committed (`run_queue.sh` →

Reading [Core AI, cap 8192, N=50]:
- Tail looping falls monotonically with strength: 96% → 92% → 52% → 28% → 8% for
  a = 0, 1, 3, 6, 9.
- a = 1 does nothing measurable, which matches the earlier PyTorch forward-only sweep
  ("pure ablation has no effect").
- Closing `</think>` and boxing an answer plateau at a = 6 to 9: 21 and 20 closed, 7 and 7
  boxed.
- Accuracy is too low at this cap to rank strengths: 0 to 4 per 50, no difference
  significant.
- So a = 6 sits on the plateau for finishing behaviour; a = 9 loops less but doesn't finish
  more. Whether 6 is optimal for accuracy needs the longer cap.

## What is proven vs. not

Proven (measured here):
- The published edit runs on Core AI as an 18 KB rank-1 adapter held as runtime states.
  It reproduces the edited checkpoint's logits [Core AI fp16 vs PyTorch fp32: max
  |Δlogit| ≤ 0.18, 100% top-1].
- It toggles on, off or to any strength between calls, with no re-export and no reload:
  0.022 ms host fill, no decode slowdown, bit-identical "off".
- It costs no measurable throughput [Core AI 4bit: 225 vs 223 tok/s decode].
- On Core AI it strongly reduces reasoning loops on MATH-500 [4bit, N=50, cap 8192]:
  tail-repetition loops 48 → 14 of 50 (p = 1.2e-10), closed thinking 1 → 21 of 50
  (p = 1.9e-6). The effect grows with strength, and a = 1 does nothing.

Not proven:
- The blog's accuracy gain (7.9% → 48.1%). At cap 8192 accuracy is 1/50 vs 3/50, not
  significant. The 32K-cap run that matches the blog's budget is still running.
- That a = 6 is accuracy-optimal: only the finishing-behaviour metrics were compared, at
  cap 8192.
- Anything on iPhone or the iOS export.


## Runtime findings along the way (macOS 27.0 framework, Python `coreai.runtime`)

1. **Per-shape specialization from Python.** Each new input shape costs about 1.5 s (each
   decode step grows `position_ids`). A repeated shape costs about 5 ms; state backing
   (bytes vs Metal) makes no difference (`probe2.py`). The Python `SpecializationOptions`
   exposes no `expectFrequentReshapes`. The Swift API does, and with it decode runs at
   about 225 tok/s, hence the Swift driver.
2. **Compiler assertion during specialization (process abort).** Seen when loading through Python (default
   options, or GPU preferred):
   - **multi-token `main`** (q > 1) on Qwen3.5 4bit, *with or without* the adapter. Plain
     export, `probe4.py`: prefill + one-token `main` works, `main` with q ≥ 8 aborts;
     `prefill` works at every tested length.
   - **one-token `main` on the export whose adapter states are 1-D**; 2-D states (`u` as
     (1, 1024), `c` as (3584, 1)) avoid it. The fp16 2-D export still aborted in Python.
   - With the Swift runner's options (GPU + `expectFrequentReshapes`), every export used
     here (1-D, 2-D, plain, fp16) loads and runs.
3. **Bundled runtime (`USE_LOCAL_COREAI=1`).** It runs the 4bit adapter export, but at
   about 7.6 s per call, unusable for generation. Its full-sequence parity numbers are in
   `results/parity_4bit_local.json`.
4. **Disk.** The first fp16 load compiles with about 4 to 7 GB of compiler temp files plus a
   1.4 GB cache entry; several runs hit ENOSPC before the switch to 4bit.

## Caveats

- **Generation used the 4bit export**, chosen for disk space, not fp16/bf16 like the blog.
  4-bit changes logits by up to about 15 vs fp32 (see step 1), so absolute loop and
  accuracy rates may differ from a bf16 run. The base vs adapter comparison is matched (same
  quantized weights, problems and seeds).
- **Cap 8192 vs the blog's 32768.** The blog's edited model averages 21.7K tokens, so at
  8192 most adapter samples are cut before answering. Accuracy at 8192 is not comparable to
  the blog's.
- **N = 50 problems, 1 sample each** (the blog: 25 × 4 base, 500 × 4 edited). The problem
  set is a seeded random subset, not the blog's.
- **Sampling** is our own host implementation (presence penalty in the vLLM convention,
  then temperature, top-k 20, top-p 0.95, SplitMix64 RNG). It is not bit-compatible with
  vLLM's sampler.
- **Grading:** "strict" = the last `\boxed{}` after `</think>`, checked with math-verify;
  "lenient" = the last `\boxed{}` anywhere. The two agreed on every sample here.
- **Loop metric** is `loopstats.tail_repetition` (last 4000 chars, 30-char windows) > 0.5,
  extracted verbatim from `loopstats.py`.
- **Export path:** a local wrapper patches the stock recipe after loading; the public model
  files are unchanged. The OS-framework runs use 2-D adapter states (see runtime finding 2).
- **Runtime:** the Python `coreai.runtime` can't set `expectFrequentReshapes`, so
  generation and throughput use a standalone Swift driver against the system CoreAI
  framework. Its greedy output matches PyTorch-4bit token for token.

## Reproduce

```sh
# from the coreai-models checkout (uv environment); HF_HUB_DISABLE_XET=1 for downloads
cd <this directory>
mkdir -p data && python -c "from huggingface_hub import hf_hub_download as d; import shutil; \
  shutil.copy(d('HuggingFaceH4/MATH-500','test.jsonl',repo_type='dataset'),'data/math500_test.jsonl')"
python coreai_export.py --compression 4bit --adapter-2d --out exports/qwen35_4bit_adapter2d
python coreai_export.py --compression 4bit --no-adapter --out exports/qwen35_4bit_plain
python coreai_export.py --compression none --adapter-2d --out exports/qwen35_fp16_adapter2d
python pt4bit_ref.py                                   # PyTorch-4bit reference logits
(cd swiftgen && swift build -c release --disable-sandbox --scratch-path .build3)
python -c "import sys; sys.path.insert(0,'.'); import numpy as np, torch; from coreai_llm import dense_adapter; \
  a=dense_adapter(1.0, dtype=torch.float32); np.concatenate([a[k].numpy() for k in ['l15_u','l15_c','l19_u','l19_c']]).astype('<f4').tofile('adapter.bin')"
python parity_swift.py exports/qwen35_fp16_adapter2d fp16_2d
python parity_swift.py exports/qwen35_4bit_adapter2d 4bit_2d
swiftgen/.build3/release/wspgen bench exports/qwen35_4bit_adapter2d/model.aimodel adapter.bin results/bench_swift_adapter2d.json
python make_jobs.py --scales 0 1 --n 50 --cap 8192 --out jobs/main.jsonl
swiftgen/.build3/release/wspgen gen exports/qwen35_4bit_adapter2d/model.aimodel adapter.bin jobs/main.jsonl results/gen_main.jsonl 248046,248044 9216
python -m venv .gradeenv && .gradeenv/bin/pip install math-verify   # grader used by score.py
python score.py results/gen_main.jsonl jobs/main.jsonl && python summarize.py
```

`run_queue.sh` runs the strength sweep and the 32K-cap run the same way (`--max-context-length
33792` export for the latter).
